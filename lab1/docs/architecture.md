# Архитектура движка

Учебная работа № 3-1-1, вариант Б.3. Реализованы Maven-каркас,
универсальные модели, сервисы иерархии классов и шаблонов,
а также универсальный автомат с очередью, worker и условными переходами.
Реализованы файловое хранение и фиксация операций с историей.
`DefaultWorkflowEngine` связывает эти компоненты: управляет экземплярами,
проверяет права, фиксирует операции и восстанавливает сохранённые состояния.

## Компоненты

| Пакет / интерфейс | Ответственность |
| --- | --- |
| `catalog.Catalog` | Поиск и сохранение классов, ролей, пользователей и шаблонов; параметры принадлежат классам. |
| `catalog.CatalogService` / `catalog.model` | Иерархия классов, наследование параметров и определения каталога. |
| `template.TemplateCatalogService` / `template.model` | Поиск, наследование и копирование шаблонов; определения состояний, действий и переходов. |
| `statemachine.StateMachine` | Собственное текущее состояние, очередь сообщений, один worker и динамическая регистрация состояний, handlers и переходов. |
| `engine.WorkflowEngine` | Создание и изменение объектов, права доступа, связывание шаблона с автоматом, согласование объектов и истории. |
| `condition.ConditionEvaluator` | Сравнение параметров по определениям предикатов и вычисление ДНФ. |
| `repository.Repository` / `repository.file.FileRepository` | Контракт хранения и файловая реализация: загрузка, атомарная запись, фиксация объекта с историей. |

Зависимости: `WorkflowEngine → Catalog, StateMachineFactory, ConditionEvaluator,
Repository`; `TemplateCatalogService → Repository`. Модели расположены в подпакетах
компонентов-владельцев, общего пакета `model` нет. События и обработчики находятся
в `statemachine.event` и `statemachine.handler`, фабрика — в `statemachine.factory`.
Подробное дерево и правила размещения описаны в [packages.md](packages.md).
Автомат не зависит от каталога, хранилища, ролей и видов бизнес-объектов.
Условия подключаются к автомату через `BiPredicate<DnfCondition, Event>`.
`DefaultStateMachineFactory` связывает его с `ConditionEvaluator` и предикатами
шаблона. Сам автомат не знает конкретных классов и параметров заказа.

## Модели и данные

Java records описывают универсальные структуры, а не виды заказов.
`ProcessTemplate` содержит действия, предикаты, состояния и переходы.
Идентификаторы и операторы — строки. `ParameterDefinition.type` задаётся
значениями `integer`, `decimal`, `string`; числовые границы представлены
`BigDecimal`, отсутствие границы — `null`. `parentId = null` обозначает корневой
класс. Наследование и проверку определений классов выполняет `CatalogService`.

### Иерархия классов

`CatalogService(Collection<ObjectClassDefinition>)` — сервис чтения проверенного
снимка иерархии. Он не реализует пока весь `Catalog`: пользователи, роли,
изменение и сохранение классов остаются контрактами следующих этапов.
Входные коллекции копируются, результаты не допускают изменения.

- `getClass(classId)` возвращает определение с собственными параметрами.
- `getEffectiveParameters(classId)` возвращает `Map<String, ParameterDefinition>`:
  обход от корня к потомку, добавление новых id и полная замена совпавших id.
  Порядок соответствует первому появлению id от корня; переопределение не меняет позицию.
- `getAncestors(classId)` возвращает определения предков от родителя к корню,
  исключая исходный класс; для корня возвращается пустой список.
- `isInstanceOf(classId, expectedClassId)` проверяет совпадение или наличие
  ожидаемого класса среди предков. Обратная принадлежность и принадлежность
  соседней ветке дают `false`; неизвестный id любого аргумента — ошибка.

При создании проверяются весь каталог, неизвестные родители, циклы (включая
самоссылки), дубликаты id классов и собственных параметров, смена типа при
переопределении. Типы ограничены `integer`, `decimal`, `string`; для числовых
типов границы необязательны, `min <= max`, границы `integer` целые.
Для строк числовые границы запрещены. Все ошибки — `IllegalArgumentException`
с контекстом. Снятие наследуемой границы через `null` допустимо: определение
заменяется целиком, а не объединяется по отдельным полям.

Значения параметров, операнды предикатов, payload и details представлены
`JsonNode`, чтобы JSON сохранял числовые и строковые типы без приведения к строкам.
Допустимость конкретных значений проверяет движок. Коллекции records и `JsonNode`
сами по себе не гарантируют глубокую неизменяемость: реализации должны управлять
копированием снимков и не выдавать наружу изменяемое внутреннее состояние.

`StateDefinition.terminal` сериализуется как `final`, поскольку `final` — ключевое
слово Java. `BusinessObject.templateId` связывает объект с шаблоном из рабочего
хранилища; `stateId` — сохраняемый снимок состояния автомата.
`InitiatorContext.userId` определяет инициатора; его роли берутся из каталога.
`HistoryEntry.timestamp` — `Instant`; файловый mapper использует `JavaTimeModule`
и отключённый `WRITE_DATES_AS_TIMESTAMPS` для ISO-8601.

## Каталог шаблонов

`TemplateCatalogService(CatalogService, Repository)` использует
абстракцию репозитория. Конструктор и операции чтения загружают актуальный
`StoreData`; отдельного несохраняемого каталога копий нет.

- `getTemplate(templateId)` находит шаблон по id.
- `resolveTemplate(classId)` ищет собственный шаблон, затем ближайшего предка.
  Если шаблона нет, бросается `IllegalArgumentException`; будущий движок должен
  выполнить это разрешение до создания объекта.
- `copyTemplate(sourceId, targetClassId, newTemplateId)` создаёт шаблон с новым id
  и целевым `classId`. Наличие наследуемого шаблона копированию не мешает;
  второй собственный шаблон класса и повторный id запрещены.
- `getTemplates()` возвращает независимые снимки всех сохранённых шаблонов.

Копирование создаёт новые определения действий, предикатов, состояний, переходов,
вложенных групп и литералов ДНФ; значения `JsonNode` копируются через `deepCopy`.
Коллекции снимков не допускают изменения. Изменение mutable JSON-значения
полученного снимка не затрагивает репозиторий и другие шаблоны.
Копия сохраняется через `Repository.update` одним новым `StoreData`, сохраняя
актуальные классы, роли, пользователей, объекты и историю. Разрешение исходного
шаблона, проверка отсутствия собственной копии и сохранение выполняются в одной
транзакции снимка. При ошибке записи сервис не публикует локальную копию.
Ошибки ввода-вывода передаются как `IOException`.
Файловая реализация синхронизирует транзакции общего документа, поэтому
копирование шаблона не затирает параллельную фиксацию другого объекта.

Проверки при загрузке ограничены обязательной структурой, уникальностью id
шаблонов и их владельцев, id действий/предикатов/состояний внутри шаблона и
корректностью ссылок на классы, роли, параметры, состояния, действия и предикаты.
Параметры ссылок включают наследуемые параметры владельца шаблона.
При копировании ссылки также должны быть допустимы для целевого класса.
Достижимость состояний, завершение процесса, неоднозначность переходов,
операторы и значения предикатов при загрузке не анализируются.
Предикаты класса проверяются на ссылку к существующему классу; при копировании
их `classId` сохраняется независимо от владельца шаблона.

`prepareStateMachineConfiguration(classId)` подготавливает только данные:
`StateMachineConfiguration` содержит реальный `classId`, начальное состояние,
снимок разрешённого шаблона и эффективные параметры **реального класса**.
Например, у `office_order` диапазон `quantity` заканчивается на 500, даже если
шаблон принадлежит `standard_order`. Evaluator получает эти эффективные
определения через каталог реального класса из контекста события.
Единственное initial-состояние требуется при подготовке конфигурации;
незавершённые шаблоны допускаются в хранилище. Автомат при подготовке не создаётся,
handlers и условия в ходе подготовки не исполняются.

## Контракт событийного автомата

`StateMachine` — интерфейс, `DefaultStateMachine` — реализация,
`DefaultStateMachineFactory` — фабрика независимых экземпляров.
Конструктор принимает id или `StateDefinition` начального состояния
и сразу регистрирует его. `initial`, `final`, роли и редактируемые параметры
сохраняются как метаданные, но не определяют поведение универсального автомата.

- `addState`, `registerHandler` и `addTransition` доступны после создания и после
  обработки событий. Строковые `registerState` и `registerTransition` сохранены
  как удобные методы. Дубликаты состояний и handlers для одной пары запрещены.
- `getCurrentState()` возвращает определение текущего состояния;
  `currentStateId()` — его id. Возвращаемые коллекции конфигурации неизменяемы.
- Переходы хранятся в `Map<StateEventKey, List<TransitionDefinition>>`, где
  `action` перехода соответствует `eventType`. `getTransitions` возвращает
  снимок списка и не теряет несколько переходов для одного ключа.
- `send` помещает `EventEnvelope(Event, CompletableFuture<EventResult>)` в
  `BlockingQueue` экземпляра. Worker получает сообщение через блокирующий `take`.
  При единственном допустимом переходе вызывает handler, если он есть,
  затем меняет состояние. Переход без handler допустим, в том числе в себя.
- Handler без перехода выполняется без смены состояния. Если для пары нет
  ни handler, ни перехода, возникает `IllegalArgumentException`.
- Проверяются условия всех переходов. Безусловный переход всегда допустим.
  При одном истинном условии выбирается этот переход; при нуле —
  `NoApplicableTransitionException`, при нескольких — `AmbiguousTransitionException`.
  Ошибки возникают до вызова handler и изменения состояния; приоритетов нет.
  Без подключённого evaluator условное событие отклоняется с `IllegalStateException`.
- `EventHandler` — функциональный интерфейс `JsonNode handle(Event)`.
  Результат обработки — `EventResult` с исходным/новым id состояния
  и JSON-результатом handler; `null` допустим. Обработчики возвращают данные,
  не изменяют состояние напрямую и пока не выполняют внешних побочных эффектов.
  Если handler бросает исключение, оно передаётся вызывающему коду,
  а состояние сохраняется. Future завершается с ошибкой, worker берёт следующее
  сообщение. Состояние публикуется одним присваиванием только после успешного
  handler и формирования результата; future завершается после публикации состояния.
- `processEvent` сохранён для совместимости как блокирующая оболочка над `send`,
  возвращающая `EventProcessingResult`. Он требует запуска автомата; вызов из
  worker запрещён, чтобы не ожидать собственное событие.

Конфигурация защищена одним коротко удерживаемым монитором `configurationLock`.
При планировании события фиксируются handler, все кандидаты и определения
их целевых состояний. При вычислении условий и исполнении пользовательского
handler монитор свободен. Поэтому новые регистрации доступны
следующим событиям, не меняя уже выбранный план текущего события.
Единственный worker последовательно исполняет события одного экземпляра,
а `volatile currentState` обеспечивает видимость текущего состояния читателям.
Снимок фиксируется при начале обработки сообщения, а не при `send`: уже стоящее
в очереди сообщение увидит регистрации, завершённые до его планирования.
Payload и `ConditionContext` события копируются при отправке. Регистрация использует только монитор
конфигурации и не ожидает исполнения handler.

### Жизненный цикл очереди

У экземпляра один platform worker и собственная `LinkedBlockingQueue<EventEnvelope>`.
До запуска lifecycle равен `STOPPED`, но первый `start` ещё разрешён;
после запроса `stop` отдельный закрывающий флаг запрещает повторный запуск.
Значения `STARTED / STOPPING / STOPPED` относятся к lifecycle, не к строковым
бизнес-состояниям. `start` идемпотентен, пока автомат работает.

`send` и начало `stop` синхронизированы одним коротким монитором `lifecycleLock`.
Проверка приёма и помещение сообщения атомарны относительно закрытия:
либо сообщение принято до внутреннего маркера остановки, либо возвращён failed future.
Маркер распознаётся по идентичности объекта, не по строке `eventType`.
Его внутренний future уже завершён. `stop` не прерывает работающий handler.
Worker сначала завершает все сообщения перед маркером, затем переходит в `STOPPED`.
Ожидание `worker.join()` выполняется за пределами обоих мониторов.
Повторный `stop` безопасен, `close` делегирует в него.
Остановка до запуска закрывает экземпляр без запуска потока.

Внешний `stop` возвращается после завершения потока; прерывание ожидающего
вызывающего потока сохраняется и восстанавливается после завершения worker.
Из handler или синхронного callback future `stop` только запрашивает остановку:
worker не может ждать себя, оставшаяся очередь будет обработана после callback.
При неожиданном прерывании или аварийном выходе worker приём закрывается,
а оставшиеся futures завершаются с ошибкой за пределами мониторов.

Очередь в памяти, без настроенного лимита и backpressure. Гарантия порядка —
FIFO по фактическому помещению в очередь, включая конкурентных отправителей;
порядок начала вызовов из разных потоков не гарантируется.
Принятое событие обрабатывается один раз в рамках работающего экземпляра,
повторных попыток и восстановления после падения процесса нет.
Отмена или таймаут ожидания future не отменяют принятое сообщение и не откатывают
состояние. Futures и callbacks завершаются вне мониторов; синхронные callbacks
могут исполняться на worker и должны быстро возвращаться.
Handlers и callbacks не должны блокирующе ждать будущие сообщения своего автомата.
Если пользовательский handler или callback не завершится, graceful `stop` будет
ждать его: принудительное завершение пользовательского кода не реализуется.

Динамическая конфигурация относится к экземпляру автомата. Изменение сохранённого
бизнес-шаблона при существующих объектах этим API не реализуется.

`WorkflowEngine` владеет отдельным автоматом на каждый объект. Он сопоставляет
`TransitionDefinition.action` с `Event.eventType`, передаёт вычисление ДНФ в guard,
фиксирует объект и запись истории одним снимком до изменения состояния автомата.
При восстановлении автомат получает сохранённый `stateId`; очередь остаётся
только оперативной памятью экземпляра и в JSON не сохраняется.

### Исполнение операций WorkflowEngine

`DefaultWorkflowEngine` зависит от `CatalogService`, `TemplateCatalogService`,
`ConditionEvaluator`, `Repository` и `StateMachineFactory`. Конструктор с Repository
собирает стандартные реализации; второй конструктор позволяет внедрить компоненты.
Файловая реализация остаётся за интерфейсом Repository. Время и единственную запись
истории для операции формирует репозиторий с внедрённым Clock.

- `createObject(userId, classId, parameters)` асинхронно проверяет шаблон,
  createRoles и типы эффективных параметров; фиксирует начальное состояние и CREATE.
- `executeAction(userId, objectId, actionId)` и `updateParameter(...)` возвращают
  `CompletableFuture<EventResult>`. Объект получает собственный `ObjectRuntime`,
  StateMachine, BlockingQueue и worker лениво при первой такой команде.
- `getObject`, `getAvailableActions`, `getHistory` читают независимые снимки Repository.
  Доступные действия не вычисляют условия, удаляют дубли, учитывают роль и final.
- `registerHandler(actionId, handler)` динамически добавляет или заменяет обработчик.
  При его отсутствии универсальный handler возвращает null, не меняя хранилище.

Каждое сообщение обрабатывается так:

1. Автомат снимает согласованный снимок состояния, handlers, переходов и hooks.
2. EventPreparer вне блокировки конфигурации загружает актуальный объект и пользователя,
   проверяет состояние, права, действие либо параметры. Для update_parameter проверяет
   editParameters. Контекст условий строится из актуальных параметров реального класса.
3. Автомат вычисляет все условия и требует единственный переход; событие редактирования
   использует handler без перехода. Отказы не вызывают handler или commit.
4. Чистый handler выполняется на worker. Его результат не меняет состояние напрямую.
5. EventCommitter подготавливает ObjectChange и вызывает Repository.commit.
   ACTION содержит старое и выбранное новое состояние; UPDATE_PARAMETER сохраняет состояние.
6. Только после успешного commit автомат присваивает новое состояние и завершает future.

Hooks — универсальные функциональные интерфейсы, настраиваемые через
`StateMachine.setExecutionHooks`. По умолчанию подготовка тождественна, commit пустой;
сам автомат не знает бизнес-модели и файлов. Hooks входят в тот же снимок конфигурации,
что и переходы. Ошибка подготовки, условия, handler или commit сохраняет прежнее состояние.
Между записью файла и присваиванием volatile-состояния есть короткое внутреннее окно;
завершённая успешная future гарантирует согласованность. При аварии в этом окне
после перезапуска авторитетным является сохранённое состояние.

`ParameterEditPolicy` принимает JSON true/false, а для обратной совместимости — массив
разрешённых id. Тип integer проверяется точно, decimal остаётся числом, string — строкой;
null допустим. Диапазоны не проверяются при создании/редактировании: это задача предикатов.
`update_parameter` зарезервирован и запрещён как пользовательское действие шаблона.

Реестр автоматов защищён lifecycleLock; приём команд и закрытие взаимоисключены.
Handlers выбираются из ConcurrentHashMap при подготовке события и не меняются для
текущей операции. Принятые создания обрабатываются одним собственным executor.
`close()` закрывает приём, завершает принятые операции, joins workers вне lifecycleLock
и освобождает реестры. Закрытие из собственного worker/callback запрещено, чтобы не
возникло ожидания самого себя. Чтение после close разрешено; повторное открытие требует
нового движка. Отмена future не отменяет принятую команду. Зависший пользовательский
handler блокирует graceful close; принудительная остановка не реализуется.

Один объект рекомендуется обслуживать одним движком. Repository сравнивает before
при commit; рассогласование сохранённого stateId с автоматом даёт CONCURRENT_MODIFICATION,
а не перезапись. Для повторной синхронизации нужен новый движок. Отдельные объекты могут
обрабатываться параллельно; общая запись файла сериализуется репозиторием без потерь.
Шаблон фиксируется через templateId при создании: поздняя копия для класса не подменяет
шаблон существующего объекта. Редактирование используемых шаблонов не поддерживается.

Отказы возвращают WorkflowException с WorkflowError: NOT_FOUND, ACCESS_DENIED,
INVALID_ACTION, CONDITION_NOT_MET, FINAL_STATE, TEMPLATE_ERROR, UNKNOWN_PARAMETER,
INVALID_PARAMETER_TYPE, PERSISTENCE_ERROR, CONCURRENT_MODIFICATION, HANDLER_ERROR,
ENGINE_CLOSED. Причина исключения сохраняется; отклонённая операция не создаёт историю.

## Условия

`DefaultConditionEvaluator(CatalogService)` реализует `ConditionEvaluator`.
`evaluate(condition, predicates, context)` вычисляет ДНФ,
`evaluatePredicate(predicate, context)` — отдельный предикат.
Локальные данные вычисления не разделяются между вызовами.

`PredicateDefinition` содержит либо `parameterId` (предикат параметра), либо
`classId` (предикат принадлежности этому классу и его подклассам).
Старый конструктор из пяти полей сохранён для предикатов параметра.
`title` остаётся необязательной описательной метаданной.

Параметр поддерживает `filled`, `=`, `!=`; числовые типы также поддерживают
`<`, `<=`, `>`, `>=`, `in_range`. `filled` означает наличие значения, поэтому
пустая строка и ноль считаются заданными. Отсутствие значения, Java null,
JSON null и MissingNode дают `false` для всех предикатов параметра.
Следовательно, `!=` с отсутствующим значением также ложно.

Сравнение определяется объявленным типом параметра. Integer преобразуется
через точный `toBigIntegerExact`, без усечения дробей и переполнения `long`;
decimal сравнивается через `BigDecimal.compareTo`, включая равенство `1.0 = 1.00`.
Строки сравниваются только на равенство/неравенство, без приведения к числам.
`in_range` проверяет включительные границы эффективного определения параметра;
отсутствующая граница не проверяется, при отсутствии обеих любое заданное число
подходит. Для `filled` и `in_range` операнд `value` не требуется.
Неизвестные ссылки, операторы, отсутствующий операнд сравнения и несовместимые
JSON-типы приводят к `IllegalArgumentException` при вычислении.
При загрузке decimal в `JsonNode` требуется `USE_BIG_DECIMAL_FOR_FLOATS`:
evaluator не может восстановить точность, потерянную до получения значения.

`ConditionContext(classId, parameters)` представляет снимок конкретного объекта,
включая полные копии JSON-значений; `ConditionContext.from(BusinessObject)`
подготавливает его из универсальной модели. Событие получает context четвёртым
аргументом; прежний конструктор из трёх аргументов сохранён.
Для условных переходов контекст обязателен. Evaluator запрашивает эффективные
определения по **context.classId**, поэтому наследуемый шаблон использует
диапазоны и новые параметры реального класса. Предикат класса использует
`CatalogService.isInstanceOf` для этой же принадлежности.

`StateMachineFactory.create(configuration, evaluator)` создаёт незапущенный
автомат, регистрирует состояния и переходы шаблона, копирует предикаты и
связывает вычисление с `Event.context`. Handlers по-прежнему регистрирует
вызывающий код. Обычные события без зарегистрированных переходов могут
вызывать handler без смены состояния; если переходы есть, но все условия ложны,
событие отклоняется даже при наличии handler.

`DnfCondition.groups` — OR между группами, AND внутри каждой группы.
Литерал ссылается на `predicateId`; `negated: true` означает отрицание.
Например, `(p1 AND NOT p2) OR p3`:

```json
{"groups": [[{"predicateId": "p1", "negated": false}, {"predicateId": "p2", "negated": true}], [{"predicateId": "p3", "negated": false}]]}
```

Пустой OR равен `false`, пустая AND-группа — `true`. Группы и литералы
вычисляются с обычным коротким замыканием; NOT инвертирует результат,
в том числе `false` для отсутствующего значения.
`TransitionDefinition.condition = null` означает безусловный переход;
движок не вызывает evaluator для отсутствующего условия.

## Хранение и проверка

`StoreData` — единственный корневой документ: `schemaVersion`, `classes`, `roles`,
`users`, `templates`, `objects`, `history`. Шаблоны в нём — рабочие копии seed.
`src/main/resources/seed/initial-data.json` содержит учебную иерархию классов
заказов, шесть ролей, семь пользователей и шаблон `standard_order_supply` для Б.3.
Шаблон принадлежит standard_order и наследуется office_order и consumables_order;
собственный шаблон consumables_order можно сохранить через copyTemplate.
В seed ровно 10 состояний и 19 переходов исходной схемы. Условия представлены
14 предикатами и ДНФ; оплата проверяется одной условной дугой с двумя OR-группами,
а не двумя конкурирующими переходами. Параметры вычисляются по реальному классу:
office_order использует диапазон quantity 1..500.

Пять демонстрационных объектов находятся в registration и имеют по одной
начальной записи CREATE. Успешные примеры различают стандартную и офисную ветви
согласования оплаты; остальные показывают ошибочное количество, отсутствующую
продукцию и недопустимую предоплату. Значения, роли, маршруты и инструкции
описаны в [orders.md](../orders.md). Конфигурация Б.3 не добавляет Java-логику в движок.

`FileRepository.loadOrInitialize()` создаёт `data/store.json` при отсутствии файла.
Существующее хранилище не мигрируется и не дополняется новым seed.

Контракт `loadOrInitialize`: если рабочего файла нет, загрузить seed из classpath,
создать каталог и сохранить документ; иначе загрузить рабочий файл без повторного
копирования seed. `load` только читает; `save` заменяет полный снимок.
Повреждённый файл нельзя подменять seed: ошибки ввода-вывода/JSON передаются как
`IOException`. Неизвестная `schemaVersion`, отсутствующие корневые коллекции,
JSON null и лишние данные после документа также отклоняются.

### Атомарная запись

`Repository` отделён от файловой реализации. Конструктор
`FileRepository(Path, Clock)` задаёт рабочий путь и время истории;
конструктор без аргументов использует `data/store.json` и `Clock.systemUTC()`.
`AtomicFileMover` — внедряемая граница файловой операции: реализация обязана
заменять файл атомарно либо бросать исключение, не публикуя замену.
По умолчанию используется только `Files.move` с `ATOMIC_MOVE` и `REPLACE_EXISTING`.

Для одного нормализованного абсолютного пути используется общий `ReentrantLock`
внутри JVM. Под ним перечитывается актуальный документ, callback `update` получает
отдельную глубокую копию, затем готовятся сериализованный снимок и копия результата.
Это предотвращает потерю обновлений разных объектов, в том числе при работе
двух экземпляров `FileRepository` с одним путём.
Требуется использовать один путь к файлу без разных символических алиасов;
координации нескольких процессов нет.

Сериализованные байты записываются в уникальный временный файл в том же каталоге,
содержимое сбрасывается через `FileChannel.force(true)`, затем выполняется атомарная
замена. Файловый mapper использует `USE_BIG_DECIMAL_FOR_FLOATS`, сохраняя точность
decimal в параметрах, операндах и истории. Только после успешного `move` публикуется
подготовленное состояние в памяти. После замены нет дополнительной сериализации
или удаления файлов, которые могли бы сообщить об отказе уже принятой операции.
При ошибке временный файл удаляется; сбой очистки добавляется в suppressed exceptions.
`AtomicMoveNotSupportedException` передаётся вызывающему коду без fallback.
Гарантия — атомарная замена документа; отдельная гарантия сохранности при потере
питания и синхронизация каталога файловой системы не реализованы.

`load` перечитывает рабочий документ и возвращает независимый снимок.
`save` предназначен для явной полной замены документа и не объединяет изменения
устаревших снимков. Конкурентные изменения метаданных используют `update`,
операции над объектами — `commit`. Вложенные `save/update/commit` того же пути
из callback запрещены, чтобы внешняя транзакция не затёрла вложенную.

### Объект и история

`commit(ObjectChange)` — единая операция для подготовленного объекта и истории.
`ObjectChange` содержит `before`, `after`, пользователя и тип операции;
для ACTION передаётся `actionId`, для UPDATE_PARAMETER — `parameterId`.
Подготовленные данные копируются. Для существующего объекта `before` сверяется
с актуальным объектом под общей блокировкой; несовпадение даёт
`ConcurrentModificationException`, без изменения объекта и истории.

Репозиторий формирует ровно одну `HistoryEntry` с UUID и `clock.instant()`:

| operation | details |
| --- | --- |
| `CREATE` | `initialState`, полные `parameters` |
| `ACTION` | `actionId`, `oldState`, `newState` |
| `UPDATE_PARAMETER` | `parameterId`, `oldValue`, `newValue` |

Идентификатор объекта, пользователь и время находятся в полях самой записи.
CREATE требует отсутствия объекта; ACTION не меняет параметры;
UPDATE_PARAMETER меняет только названный параметр и сохраняет состояние.
Класс и привязка шаблона существующего объекта не меняются.
Права, условия переходов и значения параметров по каталогу проверяет
WorkflowEngine до передачи принятого изменения. Его отказы не вызывают commit.
Сбой подготовки или записи не добавляет историю и не публикует объект.
При каждом новом успешно принятом вызове добавляется одна запись;
идемпотентность повторных клиентских запросов по operationId пока не вводится.

Очередь и незавершённые futures не входят в `StoreData`. После аварийного завершения
процесса принятые в очередь события могут быть потеряны. После успешного commit и
падения до ответа вызывающему коду результат может быть сохранён без полученного
подтверждения; автоматическое воспроизведение сообщений не реализовано.

Проверка — `mvn clean test`: JUnit 5 тесты иерархии используют seed из classpath,
тесты шаблонов — собственные определения и тестовый `Repository`.
JSON-проверка сохранения и повторной загрузки копий работает в `@TempDir`,
а не в `data/store.json`.
Тесты автомата используют произвольные id и проверяют регистрацию во время работы,
неоднозначность, исключения, снимки конфигурации и конкурентные вызовы.
Согласование потоков в тестах выполняется через `CountDownLatch` и ограниченные
ожидания, без `Thread.sleep`.
Отдельные тесты очереди проверяют graceful shutdown, ошибки, отмену futures,
конкурентные start/send/stop, остановку из callback и аварийное прерывание worker.
Тесты evaluator покрывают типы, точность, границы и все ветви ДНФ;
интеграционные тесты используют отдельный JSON-шаблон с двумя одновременно
истинными переходами и проверяют отсутствие частичного изменения состояния.
Файловые тесты в `@TempDir` проверяют seed, восстановление, историю с фиксированным
Clock, точность decimal, атомарную замену, ошибки записи, параллельные изменения
разных объектов и запрет вложенной записи.
