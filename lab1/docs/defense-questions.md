# Вопросы к защите и ответы

Учебная работа № 3-1-1 «Приёмы моделирования бизнес-логики».

Вариант Б.3 «Управление заказом на поставку стандартной продукции».

Ответы относятся к текущей реализации проекта. Там, где возможность только
следует из модели, но не предоставлена отдельным методом приложения, это указано
явно. Примеры условий и истории ниже поясняют алгоритмы и не являются отчётом
о дополнительном запуске программы.

Учтены локальный Javalin backend, браузерная карточка с графом и историей,
а также исправление выбора класса без шаблона. Исходные десять вопросов
сохранены; пояснения о веб-слое включены в соответствующие ответы.

## 1. Что хранится в шаблоне, а что в объекте? Где здесь паттерн «Приспособленец»?

**Коротко:** шаблон хранит общие правила процесса, а объект — данные и текущее
положение одного конкретного заказа. Идея «Приспособленца» заключается в отделении
общей части от индивидуальной, чтобы не хранить полное описание процесса
в каждом заказе.

В `ProcessTemplate` находятся:

- идентификатор, название и класс-владелец шаблона;
- роли, которым разрешено создавать объекты;
- действия и определения предикатов;
- состояния с начальными и конечными признаками, ролями и политикой редактирования;
- переходы и их условия.

В `BusinessObject` находятся `id`, реальный `classId`, текущий `stateId`,
значения `parameters` и ссылка `templateId`. Например, у двух офисных заказов
могут быть разные количества, номера и состояния, но один `templateId`.
Сами определения параметров принадлежат каталогу классов, а не шаблону.
История хранится отдельно и связывается с объектом через `objectId`.

В веб-карточке это разделение видно напрямую: `/api/objects/{id}` возвращает
данные экземпляра, а `/api/objects/{id}/process` — его действующий шаблон
и `currentStateId`. Граф использует общий маршрут, но выделяет состояние
конкретного объекта по backend. Локальная история кликов статус не определяет.

В терминах Flyweight общая, разделяемая часть — описание процесса, а внешнее
индивидуальное состояние — данные конкретного объекта. Поэтому шаблон не должен
содержать одно общее поле «текущее состояние всех заказов».

**Оговорка о реализации:** здесь используется идея разделения данных, а не
полная классическая реализация Flyweight с единственным экземпляром каждого
шаблона в памяти. Сервисы возвращают независимые снимки, а фабрика создаёт
конфигурацию отдельного автомата. Общая ссылка в модели хранения не означает,
что все объекты Java обязаны ссылаться на один и тот же экземпляр `ProcessTemplate`.
Наличие слова «шаблон» также не означает использование паттерна Template Method:
наш шаблон — данные, а не базовый Java-класс с переопределяемыми шагами алгоритма.

Код: [ProcessTemplate](../src/main/java/ru/moipis/workflow/template/model/ProcessTemplate.java),
[BusinessObject](../src/main/java/ru/moipis/workflow/engine/model/BusinessObject.java).

## 2. Почему классы объектов заданы данными, а не классами языка программирования? Что это даёт и чем приходится платить?

**Коротко:** чтобы один движок мог работать с разными видами объектов без
отдельных Java-классов и методов для каждого процесса. Цена такого решения —
проверка предметной модели во время выполнения, а не компилятором.

`order`, `standard_order`, `office_order` и `consumables_order` — записи
`ObjectClassDefinition`. Их связи задаются `parentId`. Все экземпляры этих
классов представлены одним Java-типом `BusinessObject`.

Это позволяет добавлять определения классов, параметры и шаблоны в конфигурацию,
не меняя универсальные алгоритмы исполнения. Для ограничения количества офисного
заказа достаточно переопределить `quantity` в данных. Не нужен `OfficeOrder`,
который наследуется от `StandardOrder`, и не нужен специальный `if` в движке.
Изменение правил в поддерживаемом формате не требует изменения Java-кода,
но порядок загрузки и обновления рабочего хранилища всё равно нужно учитывать.

За гибкость приходится платить:

1. Компилятор не обнаруживает опечатку в `stateId`, `parameterId` или `parentId`.
   Ссылки, дубликаты, циклы и несовместимые типы проверяют сервисы.
2. Значения параметров хранятся в универсальной карте `JsonNode`, поэтому
   проверки типов выполняются явно при создании и редактировании.
3. Наследование, поиск шаблона и вычисление условий приходится реализовывать
   самостоятельно, а не получать от механизма Java-наследования.
4. Обычный рефакторинг Java не переименует автоматически идентификаторы внутри JSON.
5. Обновление модели требует правил совместимости с уже сохранёнными объектами.

Универсальность ограничена возможностями движка: новый класс или диапазон можно
описать данными, но для нового типа параметра или нового оператора потребуется
расширение Java-кода. Кроме того, правка seed не меняет существующий `store.json`:
seed используется только при первичной инициализации.

Веб-форма использует ту же универсальность: классы приходят из `/api/classes`,
поля — из `/api/classes/{classId}/parameters`, типы string/integer/decimal
определяют элементы ввода. В JavaScript нет фиксированного списка классов,
параметров или состояний Б.3. Добавление нового типа по-прежнему потребует
поддержки и в ядре, и в отображении поля.

## 3. Какой шаблон и какие параметры действуют для объекта подкласса? Что изменится, если подкласс получит собственный шаблон?

**Коротко:** параметры собираются по всей цепочке наследования, а шаблон берётся
у самого класса или ближайшего предка. Новый собственный шаблон влияет на выбор
для новых объектов, но не перепривязывает уже созданные объекты автоматически.

Для `office_order` эффективные параметры складываются из определений `order`,
`standard_order` и `office_order`. Собственный параметр добавляется, а определение
с совпавшим id полностью заменяет унаследованное. Так `quantity` получает
диапазон 1..500 вместо 1..10000. Менять его тип нельзя.

Пока собственного шаблона нет, `office_order` использует `standard_order_supply`,
принадлежащий `standard_order`. Предикаты всё равно проверяют эффективные
параметры **реального класса объекта**, поэтому количество 700 допустимо
для стандартного заказа, но не проходит `in_range` для офисного.

Если подкласс получает собственный шаблон через `copyTemplate`:

- создаются новый id и новая привязка `classId`, остальные элементы копируются глубоко;
- поиск `resolveTemplate` для этого подкласса начинает возвращать собственный шаблон;
- новые объекты создаются по нему, включая его `createRoles` и начальное состояние;
- копирование само по себе не меняет наследование параметров;
- исходный шаблон и другой подкласс остаются без изменений.

При создании движок записывает `templateId` в объект. Поэтому ранее созданные
объекты сохраняют прежнюю привязку и после перезапуска. Это привязка к id,
а не отдельная сохранённая версия содержимого шаблона. Для объекта без
`templateId` в коде предусмотрен поиск действующего шаблона по классу, но новые
объекты движок создаёт с заполненным `templateId`.

**В веб-интерфейсе нужно различать два источника.** Поле `templateId`
в `/api/classes` описывает выбор процесса для **нового** объекта этого класса;
`/api/objects/{id}/process` использует сохранённую привязку **существующего**
объекта. Поэтому после копирования шаблона форма может предлагать новый процесс,
а карточка старого заказа продолжит показывать прежний.

**Если шаблона нет:** наличие класса в каталоге ещё не означает возможность
создания объекта. У исходного `order` нет собственного шаблона и нет предка,
у которого его можно получить. Шаблон дочернего `standard_order` вверх
не наследуется. Поэтому API оставляет `order` в каталоге с `templateId:null`,
а форма предлагает классы с непустым `templateId`. Это не запрет по id:
если базовому классу назначить процесс, он тоже станет доступен.
Прямой POST без шаблона движок отклоняет; HTTP-слой возвращает
`409 / NO_PROCESS_TEMPLATE` без изменения объекта и истории. Отсутствие
процесса обозначается `NoTemplateForClassException`, а не разбором текста ошибки.

Код: [TemplateCatalogService](../src/main/java/ru/moipis/workflow/template/TemplateCatalogService.java),
[DefaultWorkflowEngine](../src/main/java/ru/moipis/workflow/engine/DefaultWorkflowEngine.java).
Веб-проекции: [WorkflowQueryAdapter](../src/main/java/ru/moipis/workflow/web/WorkflowQueryAdapter.java).
Схема: [наследование классов](diagrams/simple/rendered/domain-hierarchy.svg).

## 4. Как в вашей модели хранения представлены наследование параметров и условия в ДНФ?

**Коротко:** наследование представлено ссылкой `parentId` и собственными
определениями параметров; ДНФ — вложенными списками литералов.

У каждого класса в `classes` хранятся только его собственные параметры.
Результат объединения с параметрами предков вычисляет `CatalogService`,
а отдельный список эффективных параметров в JSON не дублируется.
Фрагмент определений из иерархии выглядит так:

```json
[
  {
    "id": "order",
    "title": "Заказ",
    "parentId": null,
    "parameters": [
      {"id": "quantity", "title": "Количество", "type": "integer", "min": 1, "max": 10000}
    ]
  },
  {
    "id": "office_order",
    "title": "Офисный заказ",
    "parentId": "standard_order",
    "parameters": [
      {"id": "quantity", "title": "Количество", "type": "integer", "min": 1, "max": 500}
    ]
  }
]
```

Это сокращённый пример: промежуточный `standard_order` и остальные параметры
опущены, но в полном каталоге они присутствуют. Класс ссылается на родителя,
а не содержит его вложенную копию.

Определения предикатов находятся в `predicates` шаблона. Условие перехода
ссылается на них по `predicateId`. Выражение `(A AND B) OR (C AND NOT D)`
представляется следующим объектом `condition`:

```json
{
  "groups": [
    [
      {"predicateId": "A", "negated": false},
      {"predicateId": "B", "negated": false}
    ],
    [
      {"predicateId": "C", "negated": false},
      {"predicateId": "D", "negated": true}
    ]
  ]
}
```

Внешний список объединяется через OR, внутренний — через AND.
`negated: true` инвертирует результат одного предиката. Это не строка
с произвольным логическим выражением: в Java используются `DnfCondition`
и `ConditionLiteral`. Если `condition` отсутствует или равен null,
переход считается безусловным. Пустой список `groups` даёт false,
а пустая AND-группа — true.

Условия вычисляет только backend. Браузер не разбирает ДНФ: DTO `/process`
передаёт состояния, переходы и подписи действий для отображения графа,
а решение о допустимости конкретного перехода принимает движок.

## 5. Как перейти от диаграммы состояний к шаблону? Какие элементы шаблона на диаграмме не видны?

**Коротко:** состояния становятся записями `states`, стрелки — `transitions`,
подписи стрелок — идентификаторами действий, а ограничения — предикатами
и условиями. Диаграмма описывает маршрут, но не всю конфигурацию процесса.

Порядок переноса:

1. Каждому бизнес-состоянию назначить стабильный строковый id и название.
2. Для начального состояния установить `initial=true`, для конечного — `final=true`.
   Точки начала и завершения на рисунке не превращаются в дополнительные состояния.
3. Собрать уникальные действия в `actions`: одно действие может встречаться
   на нескольких стрелках. Например, `approve` используется на разных этапах.
4. Для каждой стрелки создать `from`, `action`, `to` и при необходимости `condition`.
5. Описать используемые предикаты и перевести составные ограничения в ДНФ.
6. Дополнить маршрут ролями, политикой редактирования, владельцем и правами создания.

Например, стрелка `composition_approval → price_approval` с действием `approve`
становится таким переходом:

```json
{
  "from": "composition_approval",
  "action": "approve",
  "to": "price_approval",
  "condition": {
    "groups": [[
      {"predicateId": "order_number_filled", "negated": false},
      {"predicateId": "product_name_filled", "negated": false},
      {"predicateId": "supplier_name_filled", "negated": false},
      {"predicateId": "quantity_in_range", "negated": false}
    ]]
  }
}
```

По одной только схеме маршрута обычно нельзя узнать `id`, `title`, `classId`
шаблона, `createRoles`, полные определения предикатов и значения их операндов.
Роли состояний и `editParameters` также нужно задать отдельно, если они
не подписаны на рисунке. В нашей подробной диаграмме роли и редактирование
указаны внутри состояний, а ДНФ раскрыта в легенде; в упрощённой версии
эти подробности скрыты намеренно.

Определения параметров, их типы, диапазоны, пользователи и членство в ролях
вообще относятся к каталогу, а не к самому маршруту. Очередь, Java-обработчики
и атомарная запись — механизм исполнения, который из стрелок тоже не следует.
Автоматического импорта PlantUML в проекте нет: JSON-конфигурация подготовлена
вручную и проверяется тестами на соответствие 10 состояниям и 19 переходам.

Браузерный граф строится в обратном направлении — **из действующего шаблона**,
полученного через `/process`, а не из PlantUML или нарисованной вручную HTML-схемы.
Cytoscape создаёт узлы и направленные рёбра для всех записей, включая возвраты,
петли и альтернативные переходы. Клик по вершине показывает информацию;
изменение состояния возможно только через команду движку. Начальное/конечное
состояния берутся из шаблона, текущее — из backend, посещённые — из реальной истории.

Схемы: [Б.3](diagrams/simple/rendered/b3-states.svg),
[веб-интерфейс](diagrams/simple/rendered/web-ui.svg).

## 6. Как записать условие второго перехода, чтобы он срабатывал ровно тогда, когда не срабатывает первый?

**Коротко:** для двух переходов из одного состояния по одному событию нужно
задать условия `G` и `NOT G`. Второй безусловный переход не является «иначе»:
при истинном `G` получатся два допустимых перехода и ошибка шаблона.

Если первое условие — один предикат `A`, второе задаётся его отрицанием:

```json
{
  "groups": [[{"predicateId": "A", "negated": true}]]
}
```

Если первое условие составное, отрицание нужно перевести в ДНФ по законам
де Моргана. Например:

```text
Первый переход:  G = A AND B
Второй переход:  NOT G = NOT A OR NOT B
```

Для второго перехода получаются **две группы**, а не одна группа с двумя NOT:

```json
{
  "groups": [
    [{"predicateId": "A", "negated": true}],
    [{"predicateId": "B", "negated": true}]
  ]
}
```

Более общий пример:

```text
G = (A AND B) OR (C AND NOT D)

NOT G = (NOT A OR NOT B) AND (NOT C OR D)

В ДНФ:
(NOT A AND NOT C) OR (NOT A AND D)
OR (NOT B AND NOT C) OR (NOT B AND D)
```

В модели отрицание относится к литералу-предикату, а не к целому произвольному
условию, поэтому последнее выражение записывается четырьмя AND-группами.
Для сложных условий число групп при таком преобразовании может существенно вырасти.

Важно инвертировать именно логический результат, а не механически заменять
оператор. Например, при отсутствующем значении и `=`, и `!=` дают false,
поэтому `parameter != value` не всегда эквивалентно `NOT(parameter = value)`.
Отрицание через `negated` учитывает это правильно.

Пара условий `G` и `NOT G` даёт ровно один допустимый переход, если вычисление
предикатов завершается без ошибок и нет других подходящих переходов. Это
не отменяет общих проверок роли, конечного состояния и корректности события.
Если первый переход безусловный, его условие всегда true; дополнение равно
false, и второй переход при тех же предпосылках никогда не должен выбираться.

В UI двум условным переходам с одним `actionId` соответствует одна кнопка.
Список `/access` учитывает роль и состояние, но не проверяет ДНФ. Условия
вычисляются при исполнении: ноль подходящих переходов даёт
`409 / CONDITION_NOT_MET`, несколько — `409 / TEMPLATE_ERROR`. Браузер
не выбирает целевую вершину и не превращает порядок рёбер в приоритет.

## 7. Почему диапазоны проверяются условием перехода, а не при каждом изменении параметра?

**Коротко:** тип отвечает за корректность представления данных, а диапазон
в данной работе — за готовность заказа к определённому этапу процесса.
Промежуточные данные можно сохранить, но нельзя согласовать до исправления.

При создании и редактировании движок проверяет существование параметра
и соответствие типа. Строку вместо целого `quantity` он не примет.
Однако целое число 700 может быть сохранено в `office_order`, хотя его
эффективный диапазон равен 1..500.

Дальнейшая последовательность выглядит так:

1. Заказ создаётся с `quantity=700`.
2. `complete` завершает регистрацию и переводит его на согласование состава.
3. `approve` проверяет `quantity_in_range` и отклоняется.
4. Менеджер меняет количество на 100: редактирование на этом этапе разрешено.
5. Повторный `approve` проходит, если остальные проверки также истинны.

Так пользователь не теряет черновые данные и может исправлять их постепенно.
При этом переход не выпускает несогласованный заказ на следующий этап.
Границы берутся из каталога реального класса, а не зашиты в обработчике.

Это осознанное правило задания, а не универсальное требование ко всем системам.
Если бы диапазон был жёстким инвариантом данных, его следовало бы проверять
при записи. Здесь min/max проверяются именно предикатами переходов.

Поэтому веб-форма показывает диапазон как подсказку, но не устанавливает
его как блокирующие `min/max`. Параметры не становятся обязательными только
из-за наличия поля на экране; unset, null и пустая строка различаются.
При отказе backend черновые значения сохраняются. Возможность редактирования
получается из `canEditParameters` и `editableParameterIds` в `/access`,
но backend повторно проверяет права и тип при PATCH. Для final доступен
только просмотр. Числовой транспорт не округляет decimal и большие целые
обычным JavaScript Number.

## 8. Что произойдёт, если два пользователя одновременно выполнят действие над одним объектом?

**Коротко:** внутри одного WorkflowEngine команды попадут в общую очередь
этого объекта и выполнятся последовательно. Вторая проверяется уже по результату
первой, а не по состоянию, которое пользователь видел при отправке.

У одного объекта один `ObjectRuntime`, один StateMachine и один worker.
При действительно одновременных вызовах нельзя заранее обещать, какая команда
окажется первой: порядок определяется фактической постановкой в очередь.
Но две команды не исполняют обработчики одного объекта параллельно.

Перед каждой операцией worker получает актуальный сохранённый объект,
проверяет состояние, пользователя, роль и условия. Если первая команда
перевела заказ в другое состояние, вторая должна быть допустима уже там.
Если первая завершилась отказом, вторая работает с прежними данными.
Для каждой команды возвращается собственный CompletableFuture.

**Вторая команда не обязательно отклонится.** Например, `approve` встречается
на нескольких этапах Б.3. Если после первой команды есть следующий `approve`
и у второго пользователя подходящая роль, обе операции могут выполниться
и последовательно продвинуть заказ на два этапа. Проверки ожидаемого клиентом
`stateId` и автоматической дедупликации повторных запросов в API нет.

Объект и одна запись истории сохраняются вместе. Дополнительно репозиторий
под блокировкой сравнивает ожидаемый снимок `before` с актуальным объектом.
При несовпадении операция отклоняется как конфликт, а не перезаписывает
чужое изменение незаметно.

Гарантия одной очереди относится к одному движку. Два движка в одной JVM
не получают общую очередь объекта: общий файловый lock и проверка снимка
помогают обнаружить конфликты, но не заменяют единого владельца автомата.
Для нескольких процессов межпроцессная координация не реализована.

**Для HTTP действует тот же порядок:** POST/PATCH вызывают существующий
WorkflowEngine, а Javalin ожидает future через `ctx.future()`. Успешный ответ
приходит только после commit объекта и истории и публикации состояния автомата.
После успеха или отказа UI перечитывает объект, процесс, доступ и историю.
Запрещённая операция не создаёт локального перехода или фиктивного события.

Блокировка кнопок предотвращает повторные нажатия в одной карточке до ответа,
но не заменяет серверную дедупликацию между вкладками или пользователями.
После потери сетевого ответа операция могла сохраниться, поэтому UI сообщает
о неопределённости и не повторяет POST/PATCH автоматически. Сначала нужно
синхронизировать данные с backend.

Код: [ObjectRuntime](../src/main/java/ru/moipis/workflow/engine/ObjectRuntime.java),
[ObjectChangeApplier](../src/main/java/ru/moipis/workflow/repository/file/ObjectChangeApplier.java).
Схема: [HTTP-команда, очередь и фиксация](diagrams/simple/rendered/web-execute-action.svg).

## 9. Можно ли по истории узнать состояние и параметры объекта на заданную дату?

**Коротко:** данных истории достаточно для восстановления состояния и значений
параметров после принятых операций, если журнал полный. Но готового метода
«получить объект на дату» в текущем API нет: реализованы `getHistory(objectId)`
в ядре и GET `/api/objects/{id}/history` в HTTP-слое.

В истории есть исходная точка и последующие изменения:

| Операция | Данные для восстановления |
| --- | --- |
| `CREATE` | Начальное состояние и полный набор переданных начальных параметров. |
| `ACTION` | Действие, старое и новое состояния; параметры эта операция не меняет. |
| `UPDATE_PARAMETER` | id параметра, старое и новое значения; состояние не меняется. |

Для восстановления нужно найти CREATE, скопировать его параметры и состояние,
затем последовательно применить записи объекта до нужного момента:
для ACTION заменить состояние на `newState`, для UPDATE_PARAMETER установить
`newValue`. Если дата предшествует CREATE, объект ещё не существовал.
Порядок следует брать из журнала фиксации, а не из случайного порядка UUID.

Например, в условной истории в 10:00 создан заказ с количеством 700,
в 10:05 завершена регистрация, в 10:10 количество исправлено на 100,
а в 10:15 согласован состав. На 10:07 получим `composition_approval`
и количество 700; на 10:12 — то же состояние и количество 100.
Отклонённая попытка согласования между этими моментами ничего не меняет
и отдельной записи в истории принятых операций не создаёт.

Есть ограничения, которые важно оговорить:

- timestamp формируется внедрённым Clock и хранится как Instant. Записи
  с одинаковым временем упорядочиваются положением в журнале; системные часы
  не гарантируют строго возрастающее время. Для строгой временной модели
  понадобились бы дополнительные правила и последовательный номер фиксации.
- История отражает принятые изменения, а не каждое мгновение исполнения
  или все неудачные попытки пользователей.
- Журнал не хранит версии определений классов, ролей и содержимого шаблонов.
  Можно восстановить прежние значения и `stateId`, но не обязательно прежний
  смысл ограничений, если метаданные редактировались вне поддерживаемого API.

Таким образом, восстановление по операциям возможно как отдельный алгоритм,
но готовое историческое чтение и версионирование всей предметной модели
в приложении не реализованы.

**Вкладка истории показывает журнал, а не снимок объекта на дату.** Timeline
показывает дату и время, пользователя, тип операции, действие, состояния
и значения до/после из реальных записей. Номер в CREATE берётся из начального снимка, поэтому переименование
заказа не меняет старую запись. Если backend не сохранил отдельную причину,
интерфейс её не придумывает. В JSON время — Instant в UTC, на экране —
дата и время в часовом поясе браузера.

HTTP-проекция сортирует записи по timestamp для отображения. При анализе
истории с возможным переводом часов это не замена исходного порядка commit,
указанного выше. При сбое загрузки UI оставляет ранее подтверждённые записи
с предупреждением; отсутствие ответа не считается пустой историей.

## 10. Что будет с существующими объектами, если изменить шаблон, например удалить состояние, в котором они находятся?

**Коротко:** безопасное изменение используемого шаблона и миграция объектов
сейчас не поддерживаются. Удаление нужного состояния при ручной правке файла
может сделать продолжение процесса невозможным.

`templateId` закрепляет ссылку на шаблон, но не сохраняет его прежнее содержимое.
Если изменить шаблон под тем же id, одна ссылка не защищает старые объекты.
Возможны разные последствия:

1. Если после удаления состояния остались ссылающиеся на него переходы,
   проверка ссылок отклонит шаблон.
2. Если ссылки в переходах тоже удалены, объект всё равно может хранить
   прежний `stateId`. При создании его автомата фабрика не найдёт это состояние,
   и выполнение команды завершится ошибкой шаблона.
3. Уже активный автомат содержит загруженный снимок конфигурации и не получает
   автоматическое обновление из файла. Он может продолжить работать по старым
   данным, тогда как другие чтения или новый автомат увидят изменённый шаблон.
   Согласованное поведение при таком редактировании не гарантируется.

Поэтому менять `store.json` вручную во время работы нельзя считать допустимым
способом обновления процесса. Динамические `addState`, `registerHandler`
и `addTransition` универсального автомата решают другую задачу: они меняют
его конфигурацию для последующих событий, а не мигрируют сохранённые шаблоны
и бизнес-объекты.

Для полноценного развития процесса потребовались бы неизменяемые версии
шаблона и явная политика: старые объекты завершаются на старой версии,
новые создаются на новой либо выполняется проверенная миграция. В миграции
нужно задать соответствие старых и новых состояний, проверить параметры
и права, сохранить изменения и зафиксировать факт переноса в истории.
Это направление развития, а не уже реализованная возможность.

Текущая модель допускает не более одного собственного шаблона класса,
поэтому одновременные версии для того же класса потребовали бы расширения
модели каталога. `copyTemplate` предназначен для другого класса и не является
механизмом версионирования. Зато создание такой копии безопасно для исходного
шаблона: оно его не меняет и не переводит существующие объекты на новый id.

Веб-интерфейс не предоставляет редактор шаблона и команд миграции: он работает
с заказами. Перетаскивание или выбор вершины графа также не заменяют миграцию.
`/process` перечитывает действующий шаблон по привязке объекта и проверяет его
`stateId`; отсутствие состояния вызывает отказ чтения схемы. Если после
несогласованной ручной правки схема или доступ не загружаются, UI показывает
ошибку, а изменяющие элементы без подтверждённых разрешений блокируются.

## Краткая памятка по веб-расширению

| Тема | Что отвечать на защите |
| --- | --- |
| Стек | Java 21, Maven, Javalin 7.2.4, Jackson 2.20.1; HTML5/CSS3/vanilla JavaScript и fetch. Spring Boot, Node.js и npm не нужны. |
| Архитектура | WebApplication собирает существующие сервисы; контроллер оформляет HTTP, WorkflowQueryAdapter строит проекции чтения. Роли и ДНФ проверяет ядро. |
| Граф | Cytoscape.js 3.34.1 из локального WebJar: `/webjars/cytoscape/3.34.1/dist/cytoscape.min.js`. CDN и внешние шрифты не используются. |
| Пользователь | Выбор userId учебный, это не аутентификация. Смена пользователя обновляет `/access`, сохраняя карточку и положение графа; при изменившемся состоянии нужна полная синхронизация. |
| Запуск | `mvn -Pweb compile exec:java`, адрес `http://127.0.0.1:7070/`. По умолчанию `demo/web/store.json`, иной путь — `--store` или `WORKFLOW_WEB_STORE`. |
| Перезапуск | FileRepository загружает сохранённые объекты и историю; seed копируется только при отсутствии файла. Очередь и незавершённые futures на диск не пишутся. localStorage не является источником заказов. |
| Ошибки | Единый JSON `{code,message,details}`: 400 — запрос/тип, 403 — роль, 404 — ресурс, 409 — состояние/условие/отсутствие процесса, 415 — Content-Type, 500 — внутренний сбой, 503 — закрытый движок. |
| Проверки | Последний зафиксированный `clean test package` на Java 21: 379 случаев без failures/errors/skipped. Три Chrome-сценария проверяют UI отдельно и не входят в это число. |
| Разделение работы | Четыре сопоставимых блока по 25% ответственности; у каждого есть разработка, проверки и документация. Подробности — раздел 13 пояснительной записки. |

отдельное хранилище и свободный loopback-порт; обычный сервер 7070 они не изменяют.
