## Назначение

Движок исполняет процессы по JSON-шаблонам. Классы предметной области, параметры,
роли, действия, состояния, предикаты и переходы задаются данными, а не отдельными
Java-классами заказов. Идентификаторы состояний и действий — строки.

В seed описаны классы `order → standard_order → office_order / consumables_order`,
процесс из **10 состояний и ровно 19 переходов**, шесть ролей, семь пользователей
и пять примеров заказов. Шаблон принадлежит standard_order и наследуется подклассами.

В центре работы — разделение самого механизма исполнения и правил конкретного
процесса. Движок умеет находить переход, проверять права и условия, сохранять
результат. При этом он не знает, что такое согласование цены или офисный заказ:
эти понятия появляются только в JSON-конфигурации.

На примере поставки продукции реализован полный путь заказа: от регистрации
и исправления исходных данных до согласования, выполнения и завершения.
Предусмотрены и неидеальные ситуации — неверное количество, отсутствие данных,
недостаточные права, возврат на доработку и отложенное рассмотрение.
Отклонённая команда не должна оставлять следов в объекте и истории; это отдельно
проверяется тестами.

## Стек

- Java 21, Maven 3.9+.
- Jackson Databind и JavaTimeModule: JSON и Instant.
- JUnit 5: модульные, интеграционные и конкурентные проверки.
- java.util.concurrent: BlockingQueue, CompletableFuture, workers.
- PlantUML: диаграммы, исходники и готовые SVG.

Нет Spring, внешней БД, брокера сообщений или готового BPM-движка.
Дополнительный локальный веб-интерфейс работает на Javalin 7.2.4 и vanilla JavaScript.
PlantUML используется для документации и не является зависимостью приложения.

### Что сделано

В приложении собран воспроизводимый сценарий, который использует настоящие
компоненты и проходит как успешные операции, так и ожидаемые отказы:

1. Инициализация настоящего FileRepository, каталогов и WorkflowEngine.
2. Создание office_order менеджером; сохранение quantity=700.
3. Завершение регистрации и отказ согласования состава: 700 вне 1..500.
4. Исправление quantity=100 и успешные согласования состава и цены.
5. correction из delivery_approval в composition_approval и повторные согласования.
6. Отказ изменения параметра в payment_approval и отказ действия по чужой роли.
7. Два объекта: standard_order с предоплатой 20% проходит первую OR-ветвь,
   office_order с 40% — вторую; значения обеих ветвей выводятся отдельно.
8. Оба заказа доходят до completed; действие после завершения отклоняется.
9. Печатается история: 13 записей офисного и 8 записей стандартного заказа.
   Четыре ожидаемых отказа не меняют объекты и не добавляют историю.
10. В отдельном запущенном StateMachine регистрируются состояние, handler и
    переход; событие через очередь выполняет `idle → configured`.
    Основной шаблон Б.3 не изменяется.

Такой порядок позволяет проследить причинно-следственную связь: сначала движок
принимает типизированное значение 700, затем условие процесса отклоняет его для
офисного заказа, а после исправления на 100 тот же переход выполняется успешно.
Это не заранее напечатанный результат: каждая команда проходит через движок,
очередь и файловое хранилище.

Успешный запуск заканчивается строкой `DEMO OK` и `BUILD SUCCESS`.
Неожиданная ошибка, отсутствие ожидаемого отказа или изменение данных после отказа
прерывает демонстрацию с ошибкой. Workers закрываются через try-with-resources.

## Архитектура

| Компонент | Ответственность |
| --- | --- |
| CatalogService | Иерархия классов, эффективные параметры, isInstanceOf. |
| TemplateCatalogService | Ближайший шаблон предка, копирование и подготовка конфигурации. |
| WorkflowEngine | Создание объектов, права, действия, редактирование, история и жизненный цикл workers. |
| ObjectRuntime | Связь одного объекта с одним StateMachine; prepare и commit. |
| StateMachine | Универсальное последовательное исполнение событий, обработчики и собственное состояние. |
| ConditionEvaluator | Типизированные предикаты и ДНФ по реальному классу объекта. |
| Repository / FileRepository | Чтение снимка и атомарная фиксация объекта с одной историей. |

У каждого активного BusinessObject свой лениво создаваемый автомат.
Состояние восстанавливается из сохранённого stateId, шаблон фиксируется templateId.
Модели не содержат Java-наследования Order/OfficeOrder.

Это разделение помогает менять предметные данные независимо от механизма
исполнения. Например, ограничение количества для офисного заказа находится
в каталоге, условие согласования — в шаблоне, а проверка диапазона — в общем
вычислителе. Для такого отличия не нужен отдельный класс или специальный метод.

## Очередь и динамическая регистрация

`executeAction` и `updateParameter` проходят через общую FIFO-очередь объекта.
`send` помещает EventEnvelope с Event и CompletableFuture в BlockingQueue;
один worker последовательно обрабатывает сообщения. Разные объекты имеют разные
workers; для создания используется отдельный служебный executor.

Для одного заказа обработка остаётся последовательной: две команды не меняют
его одновременно. Если отправить исправление количества, а следом согласование,
вторая команда будет проверять уже исправленные данные. CompletableFuture
передаёт результат или причину отказа вызывающему коду; новый поток на каждое
сообщение не создаётся. Разные заказы могут обрабатываться параллельно, поэтому
запись общего JSON-файла защищена отдельно.

Событие получает согласованный снимок конфигурации. Права и актуальные параметры
проверяются внутри очереди, затем вычисляются условия всех дуг. Один истинный
переход исполняется; ни одного — отказ, несколько — ошибка шаблона.
У события может быть handler без смены состояния.

Handler не меняет внутреннее состояние напрямую. Commit hook сохраняет объект и
историю; только после успеха автомат публикует новое состояние и завершает future.
Исключение handler или ошибка записи сохраняет прежние данные и не останавливает worker.

`addState`, `registerHandler`, `addTransition` доступны после start.
Реестр не блокируется на время пользовательского handler. Регистрация действует
на последующие сообщения. Это возможность универсального автомата, а не API
редактирования сохранённого бизнес-шаблона при существующих объектах.

`close` прекращает приём, завершает принятую очередь и ожидает workers.
Handlers и синхронные callbacks не должны ждать сообщения того же worker.
WorkflowEngine.close вызывается снаружи его workers и callbacks.

## Параметры, условия и права

Параметры собираются от корня к потомку. Совпавший id полностью заменяет
определение, но менять тип нельзя. Типы: integer, decimal, string.
Создание и редактирование проверяют типы, но не min/max. Диапазоны проверяются
переходами через in_range с эффективным определением реального класса.

ДНФ представлена OR-списком AND-групп из литералов predicateId/negated.
Поддерживаются filled, =, !=, <, <=, >, >=, in_range и предикат принадлежности классу.
Decimal сравнивается как BigDecimal, целые — точно через BigInteger.
Отсутствие/null даёт false; NOT может превратить его в true.
filled считает заданными ноль и пустую строку, поэтому block_reason очищается null.

Создание требует пересечения ролей пользователя с createRoles, действия —
с ролями текущего состояния. Редактирование Б.3 разрешено только в registration
и composition_approval. completed запрещает все изменения.
Доступные действия уникальны и не фильтруются по условиям.

## Хранение

Seed копируется только при отсутствии рабочего файла. Существующий store.json
не перезаписывается и автоматически не мигрируется. Повреждённый JSON вызывает
ошибку, а не сброс данных. Repository.load возвращает независимый снимок.

StoreData содержит schemaVersion, classes, roles, users, templates, objects, history.
`commit(ObjectChange)` атомарно сохраняет объект и ровно одну запись CREATE,
ACTION или UPDATE_PARAMETER с временем внедрённого Clock.

Новый снимок пишется во временный файл рядом с рабочим, сбрасывается через
FileChannel.force(true), затем используется Files.move с ATOMIC_MOVE и
REPLACE_EXISTING. Если атомарная замена недоступна, операция отклоняется:
fallback к обычному копированию отсутствует. Запись общего снимка синхронизирована
внутри JVM, изменения разных объектов не теряются.

## Известные ограничения

- Очереди хранятся только в памяти: аварийное завершение может потерять принятые
  сообщения. Commit может сохраниться без полученного клиентом подтверждения.
- Нет брокера, повторного воспроизведения, дедупликации запросов или распределённой транзакции.
- Очередь не ограничена; backpressure и вытеснение неактивных автоматов отсутствуют.
- Один platform worker на активный объект допустим для учебной, не массовой нагрузки.
- Файловая запись сериализует общий JSON и копирует весь снимок; межпроцессной блокировки нет.
- Один объект рекомендуется обслуживать одним движком. Внешнее рассогласование
  обнаруживается, а не автоматически исправляется.
- Нет изменения используемых шаблонов и автоматической миграции уже созданного хранилища.
- Отмена future не отменяет принятую операцию. Незавершающийся handler задерживает close.
- Нет отдельной гарантии сохранности при отключении питания и fsync каталога.
- `update_parameter` — зарезервированный внутренний eventType.
- Сборка обычного JAR не включает зависимости: запускайте демо Maven-командой,
  а не `java -jar` без classpath.

## Локальный REST backend

Требуются JDK 21 и Maven. Запуск из `lab1`:

```shell
mvn -Pweb compile exec:java
```

Сервер доступен только по `http://127.0.0.1:7070`. По этому адресу открывается
dashboard со списком заказов, поиском, фильтром состояния, выбором пользователя
и формой создания. Нажатие на заказ открывает карточку с параметрами.
Карточка включает граф процесса, доступные действия, редактирование разрешённых
параметров и историю операций. Схема и полномочия загружаются из backend.

В текущем Windows-окружении Maven уже есть в `.tools`, JDK 21 — в Rider:

```powershell
$env:JAVA_HOME='C:\Program Files\JetBrains\JetBrains Rider 2025.3.3\jbr'
& .\.tools\apache-maven-3.9.9\bin\mvn.cmd '-Dmaven.repo.local=.tools/m2' -Pweb compile exec:java
```

По умолчанию используется постоянный `demo/web/store.json`. Если его нет,
FileRepository один раз создаёт его из seed с пятью примерами заказов.
Существующий файл не сбрасывается и не перезаписывается при запуске;
повреждённый JSON останавливает запуск. `data/store.json` не затрагивается.
Другой путь задаётся аргументом (приоритет выше переменной окружения):

```shell
mvn -Pweb compile exec:java "-Dexec.args=--store demo/my-web/store.json"
```

Либо установите `WORKFLOW_WEB_STORE`. Путь может содержать пробелы:
в `exec.args` его нужно дополнительно заключить в кавычки. Используйте один
процесс/движок на JSON-store. Остановка — Ctrl+C: Jetty даёт активным запросам
до 10 секунд на завершение, затем engine завершает принятые команды и workers.
Отмена HTTP-запроса не отменяет команду; автоматически повторять POST/PATCH нельзя.

`userId` передаётся явно и обозначает выбранного учебного пользователя.
Настоящей аутентификации нет; произвольный CORS не включён. Роли, конечное
состояние, типы параметров и ДНФ проверяет существующее ядро. Контроллеры
вызывают его асинхронно через `ctx.future()`. Изменения идут через прежнюю
очередь объекта; успешный ответ формируется после commit объекта и истории.

| Метод | Путь | Назначение |
| --- | --- | --- |
| GET | `/api/users` | Пользователи и роли |
| GET | `/api/classes` | Классы и parentId |
| GET | `/api/classes/{classId}/parameters` | Эффективные определения параметров |
| GET / POST | `/api/objects` | Список / создание объекта |
| GET | `/api/objects/{id}` | Параметры, состояние и определения |
| GET | `/api/objects/{id}/process` | Сохранённый шаблон, состояния и переходы |
| GET | `/api/objects/{id}/access?userId=...` | Редактирование и уникальные действия по роли |
| GET | `/api/objects/{id}/history` | История в хронологическом порядке |
| PATCH | `/api/objects/{id}/parameters/{parameterId}` | Изменение одного параметра |
| POST | `/api/objects/{id}/actions` | Выполнение действия |

Создание принимает `{"userId":"user_manager","classId":"office_order","parameters":{"quantity":700}}`
и возвращает 201 с `Location` и карточкой. Диапазон не проверяется при создании:
для перехода потребуются заполненные параметры и истинные условия.
PATCH принимает `{"userId":"user_manager","value":100}`; явный `value:null`
очищает значение, пропущенный value — ошибка 400.

Пример действия над исходным seed-заказом:

```http
POST /api/objects/demo-office-valid/actions HTTP/1.1
Host: 127.0.0.1:7070
Content-Type: application/json

{"userId":"user_manager","actionId":"complete"}
```

Успешный ответ 200:

```json
{"previousStateId":"registration","currentStateId":"composition_approval","handlerResult":null}
```

Повторный complete уже из composition_approval отклоняется; используйте
действия, возвращённые `/access`. Этот endpoint не фильтрует действия по ДНФ:
например, approve виден для quantity=700, но его выполнение возвращает 409.
Доступ содержит также stateId и editableParameterIds для выборочной политики.
Для его реализации добавлен read-only `WorkflowEngine.getAccess`, использующий
общие проверки ядра; авторитетная проверка команды остаётся внутри worker.

Ошибки имеют формат `{"code":"CONDITION_NOT_MET","message":"...","details":{}}`.
HTTP-коды: 400 неверный запрос/тип, 403 запрет прав, 404 неизвестный ресурс,
409 действие/условие/конфликт состояния, 415 неверный Content-Type,
500 ошибка хранения/handler/конфигурации, 503 закрытый движок.
В ответах отсутствуют stack trace и внутренние сообщения серверных сбоев.
`/process` использует сохранённый templateId, включая наследованный шаблон:
появление новой копии для подкласса не меняет ранее созданные заказы.

Проверка backend и ядра: `mvn clean test`. HTTP-тесты поднимают настоящие серверы
на свободных loopback-портах с @TempDir. Они проверяют контракты, запреты,
точные числа, историю, перезапуск, очередь, ожидание atomic move и отказ записи.
Статический тестовый ресурс находится только в `src/test/resources/public`.
Подробный проект интеграции: [docs/ui-integration-plan.md](docs/ui-integration-plan.md).

## Интерфейс: список и создание заказов

Все данные загружаются через существующий backend. Кнопка «Обновить» перечитывает
заказы; после создания и возврата из карточки список также обновляется с сервера.
Классы и эффективные параметры запрашиваются при открытии формы и выборе класса.
В `/api/users` добавлены названия ролей из каталога (`roleTitles`), прежние id
в `roles` сохранены. Проверки полномочий остаются в ядре.

Поля строятся по определениям типов string/integer/decimal. Диапазоны показаны
как подсказки, без ограничивающих min/max. Незаданные поля не передаются;
режим «Значение» сохраняет в том числе пустую строку, «Очистить значение» — null.
Черновик сохраняется при backend-отказе, закрытии формы и переключении класса;
после успешного создания открывается карточка сохранённого объекта.
Черновики живут только до перезагрузки страницы. Источником заказов остаётся JSON-store
на сервере; localStorage, frontend-сборщик и npm не используются.

Браузерный smoke-тест использует Python standard library и установленный Chrome,
без pip, npm и Node.js. Он **создаёт тестовые заказы**, поэтому сервер для него
нужно запускать с отдельным временным хранилищем. Общая инструкция безопасного
запуска трёх сценариев приведена ниже, в разделе «Браузерные проверки».

Тест проверяет реальные API-запросы, поиск, фильтр, создание quantity=700,
отказ прав без потери ввода, точность чисел, безопасный вывод строк, reload,
смену класса, восстановление после недоступности сети и мобильную ширину.
Снимки desktop/mobile и результат сохраняются в `.tools/dashboard-browser/`.
Путь Chrome можно задать переменной `WORKFLOW_TEST_CHROME`, адрес сервера —
`WORKFLOW_TEST_URL`. Maven-проверки не требуют браузера.

Проверка первой части UI: `clean test package` на JDK 21 — BUILD SUCCESS,
374 случая, failures/errors/skipped = 0. Браузерный прогон в Chrome — PASS;
проверены ширины 1366 и 390 px, 34 реальных сетевых запроса без внешних ресурсов.

## Карточка, граф процесса и действия

Карточка показывает текущего пользователя и роли, класс, сохранённый шаблон,
параметры и историю. Граф строится из `/process` для любого шаблона, включая
петли, возвраты и параллельные дуги. Начальное, конечное, текущее и посещённые
состояния отличаются визуально. Посещённые состояния определяет история,
текущее — backend. Выбор узла только показывает информацию.

Используется локальный Maven WebJar `org.webjars.npm:cytoscape:3.34.1`.
Внутри dependency JAR проверен путь
`META-INF/resources/webjars/cytoscape/3.34.1/dist/cytoscape.min.js` (435503 байта).
Javalin обслуживает его по `/webjars/cytoscape/3.34.1/dist/cytoscape.min.js`;
HTTP-тест проверяет 200 и JavaScript Content-Type. CDN и Node.js не нужны.
Обычный application JAR содержит собственные UI-модули; WebJar находится
рядом в Maven classpath, который формирует существующая команда запуска.

Граф поддерживает zoom/pan и «Показать весь процесс». Все состояния и переходы
также доступны текстом. Если библиотека не загрузилась, текстовая схема остаётся
доступной, как и команды в панели действий. Размещение узлов вычисляет
библиотека; схемы Б.3 в JS нет.

Кнопки приходят из `/access`, одинаковые actionId объединяются. ДНФ не
вычисляется в браузере. Во время POST/PATCH кнопки и выбор пользователя
блокируются; статус не меняется до ответа сервера. После успеха и отказа
обновляются объект, процесс, доступ и история. При ошибке чтения доступа
изменения недоступны. Кнопки параметров учитывают canEditParameters и
editableParameterIds. Отказ PATCH сохраняет ввод; backend повторно проверяет
права и состояние. Конечное состояние оставляет только просмотр.

Проверка отдельного процесса и всех ветвей Б.3 в настоящем Chrome выполняется
сценарием `src/test/browser/order_process_smoke.py` по общей инструкции ниже.
Подготовка отказывается перезаписывать существующий store. Тестовые данные
содержат Б.3 и дополнительный процесс из трёх состояний с петлёй, параллельными
условными переходами и выборочной политикой редактирования.
Снимки и результат — `.tools/order-process-browser/`.

Итоговая проверка карточки: `clean test package` на JDK 21 — BUILD SUCCESS,
375 случаев без ошибок и пропусков. Chrome-проверки карточки и регрессия
списка/создания — PASS. В application JAR проверены все семь UI-ресурсов,
в WebJar — фактический файл Cytoscape. WorkflowEngine не менялся на этапе карточки.

## История изменений и UX

В карточке есть вкладки «Обзор заказа» и «История изменений». Timeline получает
только подтверждённые записи `GET /api/objects/{id}/history`: дату и время
в часовом поясе браузера, пользователя, тип операции, состояния, действие,
название параметра и значения до/после. Раскрываемая запись создания показывает
исходный снимок параметров, включая первоначальный номер заказа. Переименование
заказа не переписывает его историю. Причина отображается только при её наличии
в записи backend; новое событие при отказе не создаётся.

После POST/PATCH карточка перечитывает объект, процесс, доступ и историю.
Уведомления различают ожидание подтверждения, успех и ошибку; backend-отказ
сохраняет введённое значение. Если команда сохранена, но последующее чтение
не удалось, уведомление явно сообщает об этом. Повторное нажатие блокируется,
одновременные обновления карточки объединяются. Ошибка чтения истории оставляет
прежние подтверждённые записи с предупреждением; успешный пустой ответ
показывается отдельно.

Смена учебного пользователя обновляет только `/access`, если состояние не
изменилось. Сохраняются карточка, вкладка, раскрытые записи, масштаб и положение
графа. Устаревшие ответы отбрасываются. Вкладки поддерживают стрелки/Home/End,
есть видимый keyboard focus, labels и aria-live уведомления. Макет проверен
при ширине 1366/1024/390/320 px; внешние шрифты и CDN не используются.

## Браузерные проверки

Нужны Java 21, Maven, Python 3 и установленный Chrome; pip/npm не нужны.
Тесты создают заказы. Сначала подготовьте **новое** отдельное хранилище
(существующий файл не перезаписывается):

```shell
python src/test/browser/history_ux_smoke.py --prepare .tools/browser-checks/store.json
mvn test-compile exec:java "-Dapplication.mainClass=ru.moipis.workflow.web.BrowserTestServer" "-Dexec.classpathScope=test" "-Dexec.args=.tools/browser-checks/store.json .tools/browser-checks/server-url.txt"
```

Тестовый launcher находится только в test classpath. Он проверяет маркер
fixture и выбирает свободный порт на 127.0.0.1, сохраняя адрес в server-url.txt.
Основной сервер по-прежнему слушает 127.0.0.1:7070. Во втором PowerShell:

```powershell
$env:WORKFLOW_TEST_URL = Get-Content -Raw .tools/browser-checks/server-url.txt
python src/test/browser/history_ux_smoke.py
python src/test/browser/order_process_smoke.py
python src/test/browser/dashboard_smoke.py
```

Все сценарии проверяют маркер временного хранилища и отказываются выполнять
запросы изменения на обычном сервере 7070. После проверки остановите тестовый
launcher через Ctrl+C. Результаты и снимки находятся в `.tools/history-ux-browser/`,
`.tools/order-process-browser/` и `.tools/dashboard-browser/` соответственно.
`mvn clean test` запускает полный набор Java/HTTP-тестов без браузера.

Проверка этапа истории и UX: `clean test package` на JDK 21 — BUILD SUCCESS,
375 случаев, failures/errors/skipped=0. Все три Chrome-сценария — PASS.
Проверено наличие восьми UI-ресурсов в application JAR; бизнес-логика не менялась.
Лог сборки: `.tools/history-ux-final-build.log`.
