# Универсальный движок бизнес-процессов

Дисциплина: **«Модели объектов и процессов информационных систем»**.
Учебная работа **№ 3-1-1 «Приёмы моделирования бизнес-логики»**.
Вариант **Б.3 «Управление заказом на поставку стандартной продукции»**.

## Назначение

Движок исполняет процессы по JSON-шаблонам. Классы предметной области, параметры,
роли, действия, состояния, предикаты и переходы задаются данными, а не отдельными
Java-классами заказов. Идентификаторы состояний и действий — строки.

В seed описаны классы `order → standard_order → office_order / consumables_order`,
процесс из **10 состояний и ровно 19 переходов**, шесть ролей, семь пользователей
и пять примеров заказов. Шаблон принадлежит standard_order и наследуется подклассами.

## Стек

- Java 21, Maven 3.9+.
- Jackson Databind и JavaTimeModule: JSON и Instant.
- JUnit 5: модульные, интеграционные и конкурентные проверки.
- java.util.concurrent: BlockingQueue, CompletableFuture, workers.
- PlantUML: диаграммы, исходники и готовые SVG.

Нет Spring, внешней БД, брокера сообщений, GUI, REST API или готового BPM-движка.
PlantUML используется для документации и не является зависимостью приложения.

## Сборка и все тесты

Выполняйте команды из корня проекта. `JAVA_HOME` должен указывать на JDK 21;
проверьте `mvn -version`.

```shell
mvn clean test
mvn clean package
```

Полный актуальный результат, перечень методов и матрица требований раздела 8 —
[docs/testing.md](docs/testing.md). Временные хранилища тестов создаются через
`@TempDir`; рабочий `data/store.json` не используется.

## Запуск демонстрации

```shell
mvn compile exec:java
```

Главный класс — `ru.moipis.workflow.demo.DemoApplication`.
[exec-maven-plugin](https://www.mojohaus.org/exec-maven-plugin/java-mojo.html)
настроен в pom.xml; вручную собирать classpath не нужно.

При каждом запуске создаётся **новый** `demo/run-<случайный суффикс>/store.json`.
Каталог игнорируется Git и сохраняется для просмотра результатов.
Демо не принимает путь к существующему хранилищу и не изменяет пользовательский
`data/store.json`. Повторный запуск не перезаписывает предыдущую демонстрацию.
Русский вывод приложения записывается в UTF-8; терминал должен поддерживать UTF-8.

### Что показывается на защите

1. Инициализация настоящего FileRepository, каталогов и WorkflowEngine.
2. Создание office_order менеджером; сохранение quantity=700.
3. Завершение регистрации и отказ согласования состава: 700 вне 1..500.
4. Исправление quantity=100 и успешные согласования состава и цены.
5. correction из delivery_approval в composition_approval и повторные согласования.
6. Отказ изменения параметра в payment_approval и отказ действия по чужой роли.
7. Два объекта: standard_order с предоплатой 20% проходит первую OR-ветвь,
   office_order с 40% — вторую; значения обеих ветвей выводятся отдельно.
8. Оба заказа доходят до completed; действие после завершения отклоняется.
9. Печатается история: 13 записей офисного и 8 записей стандартного заказа.
   Четыре ожидаемых отказа не меняют объекты и не добавляют историю.
10. В отдельном запущенном StateMachine регистрируются состояние, handler и
    переход; событие через очередь выполняет `idle → configured`.
    Основной шаблон Б.3 не изменяется.

Успешный запуск заканчивается строкой `DEMO OK` и `BUILD SUCCESS`.
Неожиданная ошибка, отсутствие ожидаемого отказа или изменение данных после отказа
прерывает демонстрацию с ошибкой. Workers закрываются через try-with-resources.

## Архитектура

| Компонент | Ответственность |
| --- | --- |
| CatalogService | Иерархия классов, эффективные параметры, isInstanceOf. |
| TemplateCatalogService | Ближайший шаблон предка, копирование и подготовка конфигурации. |
| WorkflowEngine | Создание объектов, права, действия, редактирование, история и жизненный цикл workers. |
| ObjectRuntime | Связь одного объекта с одним StateMachine; prepare и commit. |
| StateMachine | Универсальное последовательное исполнение событий, обработчики и собственное состояние. |
| ConditionEvaluator | Типизированные предикаты и ДНФ по реальному классу объекта. |
| Repository / FileRepository | Чтение снимка и атомарная фиксация объекта с одной историей. |

У каждого активного BusinessObject свой лениво создаваемый автомат.
Состояние восстанавливается из сохранённого stateId, шаблон фиксируется templateId.
Модели не содержат Java-наследования Order/OfficeOrder.

## Очередь и динамическая регистрация

`executeAction` и `updateParameter` проходят через общую FIFO-очередь объекта.
`send` помещает EventEnvelope с Event и CompletableFuture в BlockingQueue;
один worker последовательно обрабатывает сообщения. Разные объекты имеют разные
workers; для создания используется отдельный служебный executor.

Событие получает согласованный снимок конфигурации. Права и актуальные параметры
проверяются внутри очереди, затем вычисляются условия всех дуг. Один истинный
переход исполняется; ни одного — отказ, несколько — ошибка шаблона.
У события может быть handler без смены состояния.

Handler не меняет внутреннее состояние напрямую. Commit hook сохраняет объект и
историю; только после успеха автомат публикует новое состояние и завершает future.
Исключение handler или ошибка записи сохраняет прежние данные и не останавливает worker.

`addState`, `registerHandler`, `addTransition` доступны после start.
Реестр не блокируется на время пользовательского handler. Регистрация действует
на последующие сообщения. Это возможность универсального автомата, а не API
редактирования сохранённого бизнес-шаблона при существующих объектах.

`close` прекращает приём, завершает принятую очередь и ожидает workers.
Handlers и синхронные callbacks не должны ждать сообщения того же worker.
WorkflowEngine.close вызывается снаружи его workers и callbacks.

## Параметры, условия и права

Параметры собираются от корня к потомку. Совпавший id полностью заменяет
определение, но менять тип нельзя. Типы: integer, decimal, string.
Создание и редактирование проверяют типы, но не min/max. Диапазоны проверяются
переходами через in_range с эффективным определением реального класса.

ДНФ представлена OR-списком AND-групп из литералов predicateId/negated.
Поддерживаются filled, =, !=, <, <=, >, >=, in_range и предикат принадлежности классу.
Decimal сравнивается как BigDecimal, целые — точно через BigInteger.
Отсутствие/null даёт false; NOT может превратить его в true.
filled считает заданными ноль и пустую строку, поэтому block_reason очищается null.

Создание требует пересечения ролей пользователя с createRoles, действия —
с ролями текущего состояния. Редактирование Б.3 разрешено только в registration
и composition_approval. completed запрещает все изменения.
Доступные действия уникальны и не фильтруются по условиям.

## Хранение

Seed копируется только при отсутствии рабочего файла. Существующий store.json
не перезаписывается и автоматически не мигрируется. Повреждённый JSON вызывает
ошибку, а не сброс данных. Repository.load возвращает независимый снимок.

StoreData содержит schemaVersion, classes, roles, users, templates, objects, history.
`commit(ObjectChange)` атомарно сохраняет объект и ровно одну запись CREATE,
ACTION или UPDATE_PARAMETER с временем внедрённого Clock.

Новый снимок пишется во временный файл рядом с рабочим, сбрасывается через
FileChannel.force(true), затем используется Files.move с ATOMIC_MOVE и
REPLACE_EXISTING. Если атомарная замена недоступна, операция отклоняется:
fallback к обычному копированию отсутствует. Запись общего снимка синхронизирована
внутри JVM, изменения разных объектов не теряются.

## Известные ограничения

- Очереди хранятся только в памяти: аварийное завершение может потерять принятые
  сообщения. Commit может сохраниться без полученного клиентом подтверждения.
- Нет брокера, повторного воспроизведения, дедупликации запросов или распределённой транзакции.
- Очередь не ограничена; backpressure и вытеснение неактивных автоматов отсутствуют.
- Один platform worker на активный объект допустим для учебной, не массовой нагрузки.
- Файловая запись сериализует общий JSON и копирует весь снимок; межпроцессной блокировки нет.
- Один объект рекомендуется обслуживать одним движком. Внешнее рассогласование
  обнаруживается, а не автоматически исправляется.
- Нет изменения используемых шаблонов и автоматической миграции уже созданного хранилища.
- Отмена future не отменяет принятую операцию. Незавершающийся handler задерживает close.
- Нет отдельной гарантии сохранности при отключении питания и fsync каталога.
- `update_parameter` — зарезервированный внутренний eventType.
- Сборка обычного JAR не включает зависимости: запускайте демо Maven-командой,
  а не `java -jar` без classpath.
